## Deep-Dive IST Scholar — Análise Completa

**Paper analisado:** SecureDyn-FL: A Robust Privacy-Preserving Federated Learning Framework for Intrusion Detection in IoT Networks (arXiv:2601.06466, 2026)

### Metodologia (resumo em 5 pontos)
1. **Selecção dinâmica de clientes**: A cada ronda de treino FL, o servidor selecciona os N clientes com melhor qualidade de dados (medida por entropia local e volume de amostras) — reduz o impacto de clientes com dados de má qualidade sem os excluir permanentemente
2. **Layer-wise Differential Privacy**: Em vez de aplicar ruído Gaussiano uniforme a todos os gradientes, aplica orçamentos de privacidade diferentes por camada (camadas finais recebem mais ruído — contêm mais informação sensível); preserva mais utilidade nas camadas iniciais (feature extraction)
3. **Byzantine Resilience via Krum**: Antes de agregar gradientes, o servidor calcula a distância entre gradientes de clientes candidatos; os outliers (potencialmente maliciosos) são descartados antes da agregação com FedAvg
4. **Protocolo de treino adaptativo**: O learning rate adapta-se dinamicamente à convergência global — se a accuracy de validação não melhorar por K rondas, o sistema aumenta a selecção de clientes novos
5. **Avaliação multi-dataset**: Três datasets com características distintas (NSL-KDD: ataques clássicos; CIC-IDS2017: tráfego moderno; TON_IoT: IoT heterogéneo) — padrão de robustez exigido em papers IEEE de segurança

### 5 Padrões de Escrita Académica IST Identificados

1. **Notação formal antes de resultados**: Toda notação matemática (ε, δ, σ, R, K) é introduzida numa secção "Preliminaries" ou no início da secção relevante, com tabela de símbolos se ≥8 símbolos são usados — nunca usar símbolos sem definição prévia
2. **"We propose" vs "This paper proposes"**: Papers IST em inglês usam sistematicamente a voz activa na primeira pessoa do plural ("We propose", "We evaluate", "We demonstrate") — nunca "it is proposed"
3. **Estrutura de parágrafos de resultados**: Cada parágrafo de resultados segue o padrão: [observação] + [comparação com baseline] + [explicação do porquê] — não apenas listar números sem interpretar
4. **Limitações como trabalho futuro**: Em IST, limitações não são fraquezas — são trabalho futuro. A frase padrão: "X is a limitation of this work and represents a promising direction for future research" — transforma um problema em oportunidade
5. **Abstract structure (CONTEXT-PROBLEM-APPROACH-RESULTS-IMPACT)**: O abstract de 200-250 palavras segue sempre: (1) contexto do problema, (2) problema específico, (3) abordagem proposta, (4) resultados principais com números, (5) impacto/contribuição — sem este flow, o abstract não passa na revisão IST

### Lacunas e Extensões Possíveis
1. **Topologia dinâmica**: O framework assume topologia fixa — extensão natural para redes IoT ad-hoc com topologia variável
2. **Personalização federada (pFL)**: Modelo global único pode ser sub-óptimo para dispositivos IoT muito heterogéneos — personalização por cluster seria uma extensão de dissertação MEIC
3. **Análise de fairness**: Não aborda equidade entre clientes com recursos diferentes (dispositivos IoT de baixo custo vs. gateways) — tema emergente em FL
4. **Comunicação eficiente**: DP aumenta o ruído, que pode requerer mais rondas → custo de comunicação elevado; técnicas de compressão de gradientes não abordadas

## Cross-training Insights

### HACKER → DOCTOR
**Tema: Privacidade diferencial como modelo de sanitização de conteúdo**

O conceito de ε-DP (epsilon-Differential Privacy) tem um análogo directo na geração de documentos académicos pelo Doctor:

1. **Nível de exposição de dados**: Assim como DP controla quanto de um ponto de dados individual pode vazar, o Doctor deve controlar o nível de detalhe de dados pessoais em documentos — nunca incluir NIF, número de aluno, morada completa sem anonimização explícita.
2. **Ruído como sanitização**: DP adiciona ruído calibrado para proteger privacidade. Em documentos, o equivalente é a paráfrase controlada de informação sensível de terceiros antes de a incluir num relatório académico.
3. **SBOM de dependências para documentos**: A ideia de dep-scan (SBOM de dependências de software) aplica-se a documentos: o Doctor deve manter um registo de *todas* as fontes utilizadas (equivalente a um SBOM bibliográfico) para auditoria de integridade académica — detecta plágio por omissão.
4. **CWE-200 (Information Exposure)**: O Hacker classifica exposição de informação sensível como CWE-200. O Doctor deve reconhecer que um documento mal sanitizado pode ser um vector de CWE-200 — ex: incluir logs de debug com paths internos, ou dados de utilizadores reais em exemplos de dissertação.

### RIDER → DOCTOR
**Tema: Byzantine resilience como modelo de revisão adversarial**

O mecanismo Krum do SecureDyn-FL (que descarta gradientes outliers de clientes maliciosos antes de agregar) tem um análogo directo no processo de revisão de documentos:

1. **Revisão adversarial obrigatória**: Antes de submeter qualquer secção, o Doctor deve actuar como "revisor Byzantino" — tentar invalidar as claims mais importantes. Se uma claim sobreviver à revisão adversarial, é robusta o suficiente para publicação.
2. **Outlier detection nas referências**: Assim como Krum detecta gradientes outliers, o Doctor deve detectar referências outliers — citações que contrariam a narrativa principal sem justificação — e ou integrá-las na discussão ou removê-las.
3. **Quórum de evidências**: Em FL com Byzantine resilience, uma decisão requer quórum (maioria de clientes honestos). Em escrita científica, cada claim principal deve ter pelo menos 2-3 referências independentes (quórum bibliográfico) — uma única referência não é suficiente para claims fortes.
4. **Fault tolerance no pipeline de geração**: O Rider despacha agentes que podem falhar e tem protocolo de retry + escalação. O Doctor deve ter comportamento equivalente: se uma secção não pode ser completada (dados insuficientes, referências contraditórias), reportar ao utilizador em vez de fabricar conteúdo.

### DOCTOR → RIDER
**Tema: Estrutura formal de FL como modelo para orquestração multi-agente**

O protocolo FedAvg (rondas de comunicação em FL) é isomórfico ao protocolo de orquestração do Rider:

1. **Ronda de comunicação ↔ Wave de orquestração**: Em FL, cada ronda selecciona clientes, recolhe gradientes, agrega, actualiza modelo global. No Rider: cada Wave selecciona agentes, recolhe outputs, sintetiza, actualiza o estado da missão. A analogia é perfeita — o Rider já implementa isto nos MÓDULOS existentes.
2. **Client selection ↔ Agent selection**: FL com selecção dinâmica (como SecureDyn-FL) escolhe clientes com melhor qualidade de dados. O Rider deve adoptar selecção dinâmica de agentes: preferir agentes com histórico de sucesso na tarefa (baseado no manifest de reprodutibilidade — MÓDULO RID-5).
3. **Convergência com critério de paragem**: FL para quando o modelo global convergiu (δ-accuracy por K rondas). O Rider deve ter critério de paragem equivalente: se os outputs de sub-agentes não melhoram após N iterações de retry, escalate imediatamente em vez de continuar infinitamente.
4. **Heterogeneidade de clientes ↔ Heterogeneidade de agentes**: FL lida com dispositivos heterogéneos (capacidades diferentes). O Rider lida com agentes com capacidades diferentes — deve adaptar o complexity budget (MÓDULO RID-3) ao perfil do sub-agente, não usar budget fixo.

### DOCTOR → HACKER (rigor documental)
**Tema: Relatórios de segurança com rigor académico IST**

Com base nos padrões IST identificados no SecureDyn-FL:
